# FEDOT.LLM Evolve Controller

Отдельный модуль управления предложенными улучшениями и их проверками.
Он выбирает датасеты, запускает stock/patch измерения, сохраняет результаты,
восстанавливает очередь и управляет длительной кампанией.

## Где находится код

Контроллер — внутренний модуль единой библиотеки FEDOT.LLM. Основной путь на сервере:

```text
/home/anpilov.kirill2/FEDOT.LLM/
├── fedotllm/agents/evolve/controller/   # код этого модуля и README
├── pyproject.toml                      # общий пакет FEDOT.LLM
├── evolve/runs/                        # отдельный каталог каждого запуска
├── current/                            # выбранная версия всей библиотеки
└── releases/<sha256>/                   # неизменяемые версии и аудит установки
```

`fedotllm` ссылается на выбранную версию всей библиотеки через `current`.
Старый путь `evolve/controller` также указывает на `current`, поэтому оба пути
используют один код. Результаты и временные файлы создаются в выбранном `evolve/runs`.
Исходный FEDOT и его Python-окружение остаются внешними зависимостями.

## Точка входа

```bash
cd /home/anpilov.kirill2/FEDOT.LLM
python -m fedotllm.agents.evolve.controller --help
python -m fedotllm.agents.evolve.controller info
python -m fedotllm.agents.evolve.controller status \
  --workspace /home/anpilov.kirill2/FEDOT.LLM/evolve/runs/example
python -m fedotllm.agents.evolve.controller diagnose \
  --workspace /home/anpilov.kirill2/FEDOT.LLM/evolve/runs/example
```

Используйте Python согласованного окружения FEDOT для ML-команд.
`info`, `status`, `diagnose` и справка не запускают обучение. `diagnose` только
читает указанную папку запуска; он не проверяет процессы и ресурсы, ничего не
перезапускает и показывает конкретные артефакты, по которым поставлен диагноз.

| Команда | Назначение |
|---|---|
| `info` | Название модуля, путь к коду и SHA версии |
| `status` | Сохранённое состояние конкретного запуска |
| `diagnose` | Свежесть supervisor и worker heartbeat, активный датасет/сторона/этап, последние timestamped строки worker log и точные пути журналов |
| `launch` | Проверка нового запуска; запуск только с `--mode launch` |
| `serve` | Длительная кампания проверок, поиск включается через `--hunt` |
| `drain` | Проверка уже предложенных улучшений |

## Организация модуля

| Файл | Ответственность |
|---|---|
| `__main__.py` | Самостоятельный CLI контроллера |
| `supervisor.py` | Длительная кампания и восстановление children |
| `quality_queue.py` | Предложенные улучшения, ревизии и замороженные датасеты |
| `quality_executor.py` | Применение патча и выполнение проверок |
| `launch.py` | Проверяемый запуск в свежем каталоге с аудитом |
| `release.py` | Хеш исполняемого кода библиотеки |
| `../evaluation/pair_scheduler.py` | Общий ограниченный планировщик с round-robin и fail-closed |

Полная поставка библиотеки находится в `fedotllm/deployment/`. Старые
`controller/build_release.py` и `controller/install.py` сохранены для прежнего
формата поставки контроллера; новая поставка использует общий формат FEDOT.LLM.

Измерение FEDOT находится в соседнем `evaluation/`, управление subprocess — в
`execution/`, сохранение результатов — в `storage/`. Поиск улучшений — в `agents/`
и `discovery/`; LLM не получает финальные метрики проверки.

## Результаты запуска

### Диагностика зависаний

Для отдельного диагностического запуска задайте
`EVOLVE_QUALITY_TRACE_PROCESSES=1`. Интервал снимков задаёт
`EVOLVE_QUALITY_TRACE_INTERVAL_SECONDS` (по умолчанию 15 секунд).
Настройка применяется при старте; существующие процессы она не изменяет.

| Артефакт | Что можно увидеть |
|---|---|
| `logs/controller.stacks.txt` | На какой строке контроллер ждёт очередь, блокировку или результат |
| `worker_artifacts/quality-out-*.stacks.txt` | Файл, функция и строка каждого Python-потока worker, от импорта до записи результата |
| `worker_artifacts/quality-out-*.process-traces/manifest.jsonl` | Связь попытки с её дочерними процессами и точные пути их стеков |
| `*.process-traces/process-*.stacks.txt` | Строки выполнения дочерних процессов loky/multiprocessing |

`diagnose` читает эти сохранённые артефакты и показывает последние стеки и
повторяющиеся снимки. Отсутствие `service_status.json` больше не скрывает
доступные worker-логи и стеки; состояние supervisor при этом остаётся неизвестным.
Счётчики снимков в результате worker зафиксированы перед записью результата;
сам сбор продолжается и во время этой записи.

Это выборочные снимки, а не остановка на каждой инструкции. Они не сохраняют
значения переменных, данные или окружение. Повтор одной строки не доказывает
deadlock. Если native-вызов удерживает GIL, Python-сборщик временно не получает
снимков; native C/C++-стек он не показывает. Дочерние интерпретаторы вне обычного
запуска multiprocessing, обходящие startup hook, требуют отдельной проверки
покрытия. Один worker соответствует одной попытке; переиспользовать его pool
между разными попытками с этой диагностикой нельзя.

Диагностика не меняет бюджет обучения и не перезапускает процессы. Ошибка
сборщика записывается отдельно и не заменяет результат обучения. Для копирования
со сервера используются только точные файлы текущей попытки из manifest.

### Очередь и результаты датасетов

В `runs/<run-name>/` находятся `quality_queue/`, `quality_jobs.jsonl`,
`quality_attempts/`, `logs/`, `worker_artifacts/`, `stock_cache/` и manifest запуска.
В `logs/service_events.jsonl` дописываются переходы службы и дочерних запусков;
в `quality_jobs.jsonl` `quality_task_side_started` означает постановку стороны,
`quality_task_worker_spawned` — подтверждённое создание worker, а
`quality_task_side_finished` — сохранённый результат этой стороны. События содержат
путь к её логам и sidecar; для общего stock cache путь владельца хранится отдельно.
Если сторона ждёт общую исходную оценку, журнал пишет
`quality_task_side_waiting_stock_cache` с причиной ожидания и временем. Это
ожидание до запуска worker, а не признак активного обучения; `diagnose` показывает
его отдельно и помечает устаревшее ожидание после часа без обновлений, не прерывая
работу. События также содержат `campaign_pair_cap`, `scheduler_active_pair_slots`,
`scheduler_queued_pair_tasks` и `pair_slot_held_during_wait`: заданный лимит не
равен числу реально обучающихся worker. В кампанийном асинхронном планировщике
ожидание общей исходной оценки не занимает worker вычислений и не удерживает слот
пары; независимые датасеты могут продолжать работу. Реальные вызовы обучения
ограничены общим пулом до `campaign_pair_cap` задач. В асинхронном режиме
`scheduler_active_pair_slots` считает короткие coordination-callback, а не полный
срок жизни пары; для числа фактически выполняемых расчётов используйте
`scheduler_active_compute_workers` и его максимум `scheduler_peak_compute_workers`.
Команда `diagnose` переносит эти счётчики в `worker_checks` и дополнительно
показывает alias `scheduler_active_pair_callbacks`, чтобы не путать их с живыми
вычислениями. Heartbeat ожидания показывает, что сторона всё ещё подписана на
общий результат, но не доказывает продвижение обучения владельца; путь к логам и
sidecar владельца записывается отдельно.
Поле `stock_flight_id` — короткий SHA-256 идентификатор общего расчёта; по нему
можно связать журнал ожидания с событием владельца и его артефактами.
После восстановления оборванная попытка получает отдельное событие
`quality_task_side_interrupted`; оно не считается метрикой и не маскируется под
штатное завершение. Команда `diagnose` возвращает `dataset_checks`: для каждого
ожидаемого датасета отдельно показывает исходную и улучшенную сторону, статус,
причину отсутствующей метрики и точные пути к worker-логу/sidecar. Сторона
считается измеренной только при конечном score и `metric_observations.metric_valid`
равном `true`; один `status=ok` без этой отметки показывается как `unverified`.
При восстановлении незавершённого журнала контроллер сохраняет байты только
оборванной последней строки в файл `quality_jobs.jsonl.incomplete-tail.<sha>.bin`
перед тем, как восстановить JSONL. Повреждение в завершённых строках не
переписывается. Если в снимок
не попал каталог очереди, поле `dataset_scope_complete` показывает, что список
ожидаемых датасетов восстановлен только по сохранившимся событиям.
`worker_artifacts/quality-out-*.stages.json` обновляется каждые 30 секунд и
содержит идентификатор предложенного улучшения, датасет, сторону, попытку,
текущий этап и последнюю строку FEDOT. Heartbeat означает только то, что worker
может сохранить состояние; сам по себе он не доказывает продвижение fit или метрику.
Внутри `fit` sidecar также хранит последнюю распознанную фазу FEDOT:
`initial_assumption_fit`, `composition`, `tuning`, `initial_assumption_fallback`,
`post_search_fit` или `fit_complete`, её
время и исходную строку журнала. `post_search_fit` означает, что FEDOT сообщил о
завершении генерации модели; дальше полный fit может ещё идти или быть пропущен.
Только `Final pipeline was fitted`/`Already fitted initial pipeline is used`
подтверждают выход из этой части `fit`. Возраст фазы не обновляется обычным
worker-heartbeat. Если worker оборвался по deadline, диагноз сохраняет последнюю
фазу вместе с точными путями worker log и sidecar; отсутствие фазы остаётся
неопределённым, а не подменяется выводом о deadlock.
Спецификация worker сначала проходит `validate_spec`; затем подготовка runtime-путей
и импорт `fedot.api.main` идут отдельными этапами (`import` и `fedot_import`).
Так сбой локальной среды не классифицируется как ошибка предложенного улучшения.
Приёмка требует полные proposal/task/side/attempt identity в событии и sidecar и
отклоняет неполные артефакты.
В heartbeat и результате стороны есть `cpu_accounting`: накопленные user/system
CPU-секунды worker и, если доступны, уже завершившихся и учтённых дочерних
процессов; также записываются разницы с предыдущим heartbeat и среднее число
учтённых CPU-ядер за этот интервал. Для дочерних процессов применяется
`resource.getrusage(RUSAGE_CHILDREN)`, поэтому живые дочерние workers могут пока
не попасть в значение. `scope` и `source` нужны для интерпретации: это счётчик
конкретного worker, а не утилизация сервера. Низкое значение не различает
ожидание диска/сети, sleep, блокировку и незавершённую дочернюю работу. Если
платформа или счётчик недоступны, поле помечается `unavailable`, что не влияет
на обучение.
Диагноз читает точную локально доступную копию worker log: показывает последнюю
timestamped строку, последний распознанный FEDOT marker и отдельно сохраняет
sidecar claims. Если raw log содержит более поздний распознанный marker, возраст
тишины считается по нему, а не по устаревшему sidecar. Обычное предупреждение,
например о необязательной зависимости, не считается продвижением optimizer.
Marker `Generation num` или число оценённых individuals подтверждает событие
optimizer, но не конечную метрику; сообщение `WindowSizeSelector` получает состояние
`fit_activity_observed` и подтверждает только активность fit-пути, не новую generation.
Диагноз `stale_evaluation` означает,
что последний распознанный marker старше часа; `fit_without_optimizer_evidence`
означает, что worker долго находится в `fit`, но marker не найден. Это сигнал для
проверки точных логов и sidecar, не доказательство deadlock и не автоматическое
завершение worker. Timestamped строки без timezone трактуются как UTC, как и
времена worker sidecar; время изменения скопированного файла не используется.

`Fedot.timeout` и общий предел стороны — разные бюджеты. В FEDOT 0.7.5 прежний
режим `legacy` распределял время по стадиям, а финальная проверка выбранного графа
и обучение на полном наборе могли продолжаться после поиска. Профиль `v11`
включает для контролируемых измерений `timeout_policy="return_best"`: один
монотонный срок FEDOT охватывает первичную оценку, композицию, подбор параметров и
финальное переобучение. Внутри него заранее резервируются 1500 секунд на полное
переобучение и до одного полного CV-бюджета кандидата на финальную проверку;
оставшееся время доступно поиску. Бюджет оценки кандидата делится между fold’ами:
для временных рядов это 1500 секунд всего, до 500 секунд на каждый из трёх fold’ов;
для табличных задач — 900 секунд всего, до 180 секунд на каждый из пяти fold’ов.
Это потолок оценки кандидата, а не обещание, что каждый кандидат использует всё
отведённое время. Если переобучение не укладывается в резерв, уже обученная
модель сохраняется и worker всё равно пытается получить holdout-метрику. Если
обученной модели нет, результат явно записывается как `fedot_budget_timeout` без
выдуманной метрики. `max_pipeline_fit_time` действует на один граф в одном CV-fold,
а не на весь вызов `fit`; это отдельный потолок одной оценки. Для `v11` FEDOT
ведёт один монотонный срок на все fold оценки кандидата, перед каждым fit
уменьшает его лимит по оставшемуся времени и отбрасывает неполный набор
fold-метрик. Этот контроль кооперативный: текущий fit, подготовка данных или
расчёт прогноза могут вернуться позже срока; после возврата кандидат получает
невалидную fitness и больше не передаётся как частично измеренный. Граница
worker-процесса остаётся жёстким пределом завершения всего измерения.

Профиль `v11`: 4 CPU на задачу, до 7 пар одновременно, бюджет FEDOT 4500 секунд,
общий предел стороны 5400 секунд и внешний watchdog 10 800 секунд. До 900 секунд
вне FEDOT остаётся на загрузку, прогноз, метрику и сохранение. Это ограничивает
длительность стадий и сохраняет пригодную обученную модель при медленном финальном
переобучении, но не гарантирует конечную метрику для любого датасета: ошибки
прогноза/оценки, отсутствие успешно обученной модели и зависший native-код требуют
отдельного результата или завершения внешней границей worker. В текущем активном
прогоне используется прежняя `v10` identity; `v11` применяется только к новому
изолированному запуску после завершения активного.
Для отдельной диагностической очереди можно явно задать `--max-pair-slots 8` при
`--n-jobs 4 --cpu-quota 32`; восемь пар не включаются автоматически.
Установка модуля не запускает benchmark и не переносит старые результаты. Старые
серверные запуски остаются историческими артефактами.

## Поведение при сбоях

Основной таймаут стороны ограничивает весь worker: запуск Python, импорт FEDOT,
загрузку датасета, fit, predict и расчёт метрики. При его истечении контроллер
принудительно завершает принадлежащую worker группу процессов; ожидание вывода
после завершения тоже ограничено. Первичная и повторные проверки хранения входят
в тот же deadline и выполняются отдельно от потока наблюдения, поэтому задержка
файловой системы не может продлить worker сверх лимита. Отдельный watchdog
действует, если контроллер перестаёт наблюдать за worker. Python-пробы используют
тот же механизм завершения со своим конечным положительным лимитом.

Завершённый watchdog timeout не запускается повторно автоматически: он сохраняется
как нерешённый результат без метрики. Подтверждённый сетевой сбой или прерывание
контроллера можно повторить один раз. Это не дублирует завершённые измерения при
восстановлении очереди. При восстановлении незакрытая попытка записывается как
`quality_task_side_interrupted` с исходным attempt ID и причиной; следующий запуск
не переименовывает её в обычное завершение.
Аварийный выход без результата и повреждённый JSON дают `invalid`; следующие
датасеты продолжают выполняться. Повреждённый результат сохраняется вместе с
причиной и путём к worker log. Неверная метрика не попадает в stock cache.
Ошибка сохранения результатов останавливает работу с явной причиной.

## Параллельная работа и ресурсы

Каждая пара — один датасет и два последовательных измерения: сначала исходный
FEDOT, затем та же проверка с предложенным улучшением. Пары разных предложений
получают слоты из одной общей очереди с чередованием по предложениям. Завершение
или ошибка одной пары сразу освобождает слот; фиксированное число ядер не
закрепляется за предложением до конца его проверки.

```python
max_pairs = min(7, cpu_quota // n_jobs)
configured_cpu_slots = max_pairs * n_jobs
```

При текущем профиле это не больше 7 пар × 4 CPU = 28 настроенных CPU-слотов.
Оставшиеся 4 CPU в лимит не включены. Это предел выдачи работы, а не измеренная
утилизация: фактическая загрузка зависит от продолжительности `fit`, загрузки
данных, ожидания ввода-вывода и типа моделей. Процент в панели кластера нужно
подтверждать отдельно, и по этой настройке нельзя обещать 75%.

Стартовая волна собирает первые пары до 10 секунд, чтобы готовые предложения
получили слоты по кругу. Пустое, заблокированное или отклонённое предложение
освобождает своё место; медленная подготовка патча не удерживает готовую работу
дольше этого интервала. При системной ошибке планировщик прекращает выдачу новых
пар и отменяет пары, которые ещё не начали worker. Уже работающая изолированная
пара завершается штатно или до собственного timeout.

Лимит 3600 секунд ограничивает вычисление одной стороны (импорт, загрузка,
`fit`, прогноз, расчёт метрики и сохранение) после получения compute-слота.
Ожидание очереди не отнимает время FEDOT: оно отдельно записывается как
`scheduler_queue_wait_seconds` в событии запуска worker-а. `quality_task_side_started`
означает, что сторона поставлена на выполнение; фактический запуск процесса
подтверждает только `quality_task_worker_spawned`. Если лимит вычисления
истекает, контроллер
завершает изолированную группу процессов worker и сохраняет точную стадию и
время; это ограниченный аварийный исход без метрики, а не доказательство, что
FEDOT штатно завершил работу. Guardian с пределом 10800 секунд защищает случай,
когда сам контроллер перестал обслуживать worker. В этот же срок входят ожидание
общего stock-кэша и межпроцессной блокировки после выделения compute-слота:
истечение до создания worker записывается как `timeout_kind` с
`worker_spawned=false`, без фиктивного worker log. В лог выводятся полная
длительность вычисления, отдельное ожидание очереди и оставшийся worker-бюджет.
Timeout не повторяется
автоматически: без конечной метрики улучшение остаётся непроверенным, без
решения KEEP/DROP.

`launch` разрешает путь `fedotllm` до физического каталога версии и сохраняет его
в `launch_audit.json`. Эта версия используется в `cwd` и `PYTHONPATH` дочернего
Python, поэтому изменение `current` не подменяет библиотеку уже выбранного запуска.

`completion=all_measured` означает наличие полных измерений по каждому требуемому
датасету. Старые записи `skipped` возвращаются в очередь: сначала используются
сохранённые `required_task_ids`, затем сохранённая область проверки, а при
утерянной области — весь реестр. Пропуск не считается завершением и не позволяет
службе выйти с успешным кодом. Если требуемые датасеты невозможно восстановить,
результат остаётся ошибкой проверки, а не вердиктом качества. Событие считается
измеренным только при `status=ok`, конечном score и
`metric_valid=true` у обеих сторон. Завершённая очередь с ошибками получает
`terminal_with_errors`; это не подтверждение качества всех улучшений. Локальные проверки с реальными аварийными subprocess подтверждают
обработку сбоев, а устойчивость на реальном FEDOT требует серверного прогона.
# Защита хранения в новых проверках

Новый протокол `disabled-sqlite-v1` отключает публичные кэши FEDOT одинаково
для исходной и изменённой сторон. Worker проверяет флаги и отсутствие объектов
кэша до и после обучения. Сам препроцессинг остаётся включённым. Отключение
кэшей может изменить производительность и случайную траекторию поиска;
production registry имеет новый identity, прежние baseline не переиспользуются.

Launcher требует 12 GiB свободного места перед созданием запуска. Во время
вычислений контроллер сохраняет резерв 4 GiB и 4096 свободных inode: при
исчерпании резерва отменяет только собственных работников, оставляет очередь
неизмеренной и сохраняет `storage_error`. После ошибки хранения автоматический
повтор запрещён, включая случай, когда итог сохранился лишь в launch log.
Старые результаты, журналы и кэши эта защита не удаляет.

Периодические проверки резерва выполняются одним общим ограниченным daemon-thread.
Если файловая проверка зависнет, повторные попытки не создают новые потоки;
необработанные проверки ограничены очередью и отменяются после окончания worker.

Для повторного полного прогона указывается `--previous-run`: проверяются
конечный статус предыдущего запуска и обе его свободные application locks.
Профиль `v11` остаётся 4 CPU на сторону, до 7 пар, 4500 секунд бюджета FEDOT внутри
общего предела стороны 5400 секунд и 10 800 секунд внешнего watchdog.

Изолированная приёмка проверяет, что каждый реально запущенный worker оставил
непустой лог и читаемый JSON этапов в своём `worker_artifacts`. Путь сверяется
после разрешения симлинков, а доступные поля датасета, стороны и попытки должны
совпадать с событием очереди. Cache hit и singleflight/recovery reuse учитываются
отдельно, поскольку они не запускают новый worker. Пропавший файл, пустой лог,
неверный JSON или выход за каталог артефактов записываются в
`acceptance.json` и делают приёмку неуспешной; временные spec/result файлы не
обязаны сохраняться после завершения.
