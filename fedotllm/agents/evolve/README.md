# EvolveAgent

EvolveAgent самостоятельно ищет улучшения в исходниках
[FEDOT](https://github.com/aimclub/FEDOT), предлагает патчи и проверяет их
на реальных задачах AutoML.

Главный принцип: **агент ищет, отдельный контроллер принимает решение**.
LLM не видит результаты финальной оценки и не может подстроиться под них.

Цели, ограничения, скоуп и схема решения:
[дизайн-документ](../../../docs/ml_system_design_doc.md).

## Термины

- **Предложенное улучшение** — гипотеза об изменении FEDOT и соответствующий патч.
- **Ревизия улучшения** — конкретная версия патча и гипотезы.
- **Проверка улучшения** — сравнение исходного FEDOT и FEDOT с этой ревизией на заранее выбранных датасетах.
- **Классы задач** — классификация, регрессия и прогнозирование временных рядов. Они определяют набор датасетов проверки.
- **Результат проверки** — метрики по датасетам и итоговое решение либо причина, по которой проверка не завершена.

Предложенное улучшение → проверка улучшения → датасеты выбранных классов задач → результат проверки.

## Как это работает

```text
Исходники FEDOT
      ↓
Scout → Verifier → Fixer
      ↓
Техническая проверка патча
      ↓
Очередь кандидатов
      ↓
Часовой Fedot на фиксированных задачах
      ↓
KEEP или DROP
```

Поиск и оценка разделены:

- **Hunt** быстро исследует код и создаёт кандидатов.
- **Judge** без участия LLM сравнивает исходный FEDOT и FEDOT с патчем.

## Агенты

### Scout — где искать

- получает карту репозитория и данные о реально исполненных функциях;
- читает файлы по одному, может искать символы, вызовы и документацию;
- выбирает файл и строку;
- формулирует механизм изменения и ожидаемый эффект;
- может отказаться от слабой гипотезы и перейти к следующему файлу.

Scout не получает список известных багов, результаты финального benchmark или
эталонный патч.

### Verifier — действительно ли это баг

- запускается для гипотез о нарушении поведения или публичного контракта;
- строит небольшой воспроизводящий пример;
- выполняет его на исходном FEDOT;
- проверяет, что ошибка относится к выбранному коду, а не к самому примеру;
- отклоняет неподтверждённые гипотезы.

Гипотезы об улучшении качества проходят сразу к Fixer: их нельзя подтвердить
одним локальным примером.

### Fixer — как исправить

- получает выбранное место, гипотезу и результат Verifier;
- создаёт минимальные изменения исходников;
- пишет короткую проверку различия исходного и изменённого поведения;
- исправляет патч по диагностике применения, импорта или тестов;
- сохраняет готовый кандидат для контроллера.

Fixer не видит финальные метрики. Он может улучшать патч только по техническому
фидбеку текущей ревизии.

Все этапы используют одну модель `z-ai/glm-5.3-flash`. Смена модели и fallback
запрещены, чтобы результат нельзя было улучшить простым повышением класса модели.

## Проверка кандидата

Перед дорогой оценкой патч должен:

1. примениться к чистому checkout FEDOT;
2. не ломать импорт изменённых модулей;
3. не создавать новых падений в тестах;
4. не падать на коротком проверочном запуске.

Короткий запуск не решает, хороший ли патч по качеству. Даже нулевое изменение
метрики допускается в очередь: окончательное решение принимает только Judge.

## Данные и оценка

| | Hunt | Judge |
|---|---|---|
| Зачем | Найти исполняемый код и отсеять сломанные патчи | Принять итоговое решение |
| Данные | Короткие classification, regression и time-series пайплайны | 24 classification, 8 regression, 8 forecasting; подмножество выбирается по затронутому коду |
| Запуск | Фиксированный `PipelineBuilder`, без composer и tuning | `Fedot(best_quality)`, tuning; бюджет поиска 75 минут после получения compute-слота, общий лимит стороны 90 минут с резервом на метрику; внешний watchdog 10800 секунд |
| Метрика | Только диагностический сигнал | Метрика и направление улучшения заморожены для каждого датасета в registry |
| Результат | Предложенное улучшение в очереди | KEEP / DROP после всей проверки либо явная причина незавершённой оценки |

**KEEP:** все требуемые стороны дали конечные метрики, нет регрессий и улучшены
больше половины датасетов либо минимум два датасета. Действующий алгоритм —
`evaluation/fedot_quality.py::decision_from_quality_jobs`.

**Незавершённая оценка:** timeout, ошибка исходной/изменённой версии, недостающие
датасеты или сбой инфраструктуры. Это не подтверждённое ухудшение качества.
Отсутствие composing само по себе не отменяет конечную метрику: активность поиска
сохраняется отдельно как диагностика.

Изменения общего или неизвестного кода проверяются на широком наборе. Изменения
`regression.py` затрагивают регрессию и forecasting. Сужение до датасетов с
категориальными признаками разрешено для известного изолированного helper
one-hot encoder; комментарии, строки и гипотеза агента сами по себе набор не сужают.

## Длительная кампания

[Контроллер](controller/README.md) держит очередь проверок и восстанавливает её после сбоя. Без `--hunt` он проверяет уже предложенные улучшения. С `--hunt` добавляется поиск, у него свои лимиты запросов и стоимости.

На одном датасете исходный FEDOT и версия с патчем идут по очереди. Разные пары берут слоты из общего пула: до 7 пар, 4 CPU на задачу. Сторона ограничена 5400 секундами, аварийный предел — 10800. Timeout не даёт KEEP и сам не повторяется. Смена кода или конфигурации требует нового workspace.

```bash
python -m fedotllm.agents.evolve.controller serve \
  --fedot /absolute/path/to/FEDOT \
  --workspace /absolute/path/to/campaign \
  --stock-cache /absolute/path/to/campaign/stock_cache \
  --duration-seconds 604800 --hunt --target-proposals 100 \
  --llm-max-queries 30 --llm-max-cost-usd 0.25 --hunt-total-cost-usd 10
```

### Ограничение поиска

Scout лучше видит код, исполненный короткими Hunt-пайплайнами. Полный composer,
HPO и часть `fedot/api/` сейчас покрыты хуже, потому что Hunt не запускает tuning.

## Архитектура

| Каталог | Назначение |
|---|---|
| `agents/` | Verifier и Fixer |
| `discovery/` | Scout, карта репозитория и выбор кандидатов |
| `controller/` | Кампания поиска, очередь и финальный контроллер |
| `evaluation/` | Датасеты, метрики и запуск Fedot |
| `execution/` | Изолированные checkout, применение патчей и subprocess |
| `storage/` | Журнал, checkpoint, история находок и бюджеты |
| `benchmark/` | Контрольные сценарии для проверки самого агента |

Точка входа:

```bash
python -m fedotllm.agents.evolve
```

Поиск: `doctor`, `run`, `continue`. Контроллер имеет собственные команды `info`,
`status`, `launch`, `serve`, `drain`. Прежние `quality-drain` и `quality-watch`
сохранены как совместимые точки входа.
