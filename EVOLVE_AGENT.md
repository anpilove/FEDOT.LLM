# EvolveAgent в FEDOT.LLM

Фоновая актуализация [aimclub/FEDOT](https://github.com/aimclub/FEDOT): scout → patch + test → гейты → audit.
Рантайм FEDOT остаётся CPU без LLM. Это **не** AutoML codegen пользовательской задачи.

## Метод

Подход — в духе [Agentless](https://arxiv.org/abs/2407.01489) (FSE'25): простой конвейер
**локализация → починка → валидация** без tree-search (у них SOTA при ~$0.34/issue), плюс
repo-level постановка, как в [repo-level code evolution](https://arxiv.org/pdf/2606.28279)
(в отличие от AlphaEvolve/OpenEvolve, которые эволюционируют одну функцию и требуют много компьюта).

1. **Scout** — inventory всех `fedot/**/*.py`: пути, outlines, hotspots (TODO/FIXME/bare except),
   **список модулей, у которых уже есть тест-модуль** (самые дешёвые для проверки)
   и **находки статического анализа** (`ruff`, правила `B,SIM,RET,C4,F`).
   LLM отвечает `PICK` + `WHY`.

   *Зачем линтер:* на свободный вопрос «найди что-нибудь» модель сходится в один и тот же
   файл (в наших прогонах — 5/5 раз). Линтер даёт сотни конкретных, точно локализованных
   кандидатов: на FEDOT это **377 находок по 25 правилам**, в промпт идут 40 штук
   round-robin по правилам — из **23 разных файлов**. Плюс появляется независимый
   критерий приёмки: предупреждение должно исчезнуть (как перезапуск линтера в BitsAI-Fix).
   `ruff` ищется автоматически (`ruff` → `python -m ruff` → `uvx ruff`); если его нет,
   секция просто пропускается.

   **Зондирование рантайма (`probe.py`) — источник дефектов, видимых пользователю.**
   Линтер даёт косметику: варианты A–C дали 100% успеха и ноль настоящих починок. Дефект, который
   существует лишь при исполнении, статический анализ не видит в принципе. Поэтому перед
   раундом FEDOT реально запускается на **законных, но неудобных** входах (константный
   столбец, NaN, inf, один класс в таргете, 3 строки, один признак) плюс контрольные
   наборы обычных данных. Находка — когда FEDOT отвечает **чужой внутренней ошибкой**
   (например путём к `catboost/…/target_converter.cpp`) вместо внятного сообщения.
   Контрольные наборы обязаны обучаться: это защита от «починки», которая просто
   запрещает всё подряд. Результат кэшируется по состоянию рабочего дерева
   (`git HEAD` + чистота), иначе 2 минуты зонда платились бы на каждом из 30 прогонов.
   Отключается через `FEDOTLLM_EVOLVE_PROBE=0`.

2. **Доказательство до патча (`templates.py`).** Измерено на трёх
   конфигурациях: агент спотыкается не на патче, а на **доказательстве**. У `gpt-4o-mini`
   тест не падал до правки **138 раз**; у `gpt-4o` падал, но по посторонней причине —
   она сослалась на несуществующий файл `mock_data.csv`. Пока доказательство сочиняет
   тот же, кто пишет патч, оно и остаётся узким местом.

   Для дефекта, найденного правилом линтера, доказательство не нужно изобретать: **само
   правило и есть спецификация**. Шаблон строит тест из исходника через интроспекцию —
   он не вызывает функцию и не открывает файлов, поэтому упасть по посторонней причине
   не может:

   ```python
   default = inspect.signature(Data.from_image).parameters["task"].default
   assert isinstance(default, (type(None), str, int, float, bool, bytes, tuple, frozenset))
   ```

   Каждый шаблон **проверяется на исходном коде** и попадает в список, только если
   реально падает. На FEDOT: 46 из 47 находок `B008`/`RUF012` дают тест, из них
   **35 подтверждены** (остальные 5 — модули с неустановленными зависимостями `H2O`,
   `TPOT`, `TabPFN`; там ошибка импорта, а она ничего не доказывает). Ни одного пустого
   теста, который проходил бы и до, и после правки.

   Агенту показывают список доказанных дефектов, а при выборе такого файла — готовый
   тест и **точный исходник дефектной функции с номерами строк**. Последнее появилось
   после наблюдения: получив весь файл с пятью почти одинаковыми методами, агент
   выдал четыре правки в трёх соседних методах и ни одной — в том, что проверяет тест.

   Побочный эффект важнее удобства: **тест больше не пишет тот, кто пишет патч**.
   Именно этот канал в литературе эксплуатируют агенты, подгоняя доказательство под
   решение. Runtime принудительно заменяет присланные моделью `TEST_NAME`,
   `TEST_FILE` и `TEST` на заранее построенное доказательство; одного совпадения
   имени недостаточно. Список кэшируется по состоянию дерева (144 с → 0.04 с).
   Отключается `FEDOTLLM_EVOLVE_TEMPLATES=0`.

2b. **Скан рантайма (`invariants.py`) — источник дефектов, которых линтер не видит.**
   Шаблоны из п.2 строятся интроспекцией и поэтому упираются в объектную модель.
   Этот зонд смотрит на то, как библиотека **работает**, и опирается только на её
   собственные декларации, так что ни одно значение здесь не выдумано:

   - **«объявлено = использовано».** Гиперпараметр передаётся публичным путём
     (`PipelineNode(params=…)`), пайплайн обучается, значение читается обратно с
     обученного объекта. Расхождение = приняли одно, работали с другим.
   - **Границы.** Значения берутся из объявленной области `PipelineSearchSpace`:
     оба конца интервала, середина, каждая категория. Падение на таком значении —
     дефект по определению, допустимым его назвала сама библиотека.
   - **Метаморфические свойства.** Из четырёх дефект-уровнем оставлено одно
     (повторный вызов даёт тот же ответ); остальные срабатывают на корректном
     поведении случайных лесов и понижены до наблюдений.

   Каждая операция считается в отдельном процессе, поэтому зависание и жёсткое
   падение — результат, а не потерянный прогон. На FEDOT: 65 операций из 79
   просканированы, **22 дефекта с тестом, проверенным на падение** на нетронутом
   дереве, в 8 файлах. Подробности — `INVARIANT_FINDINGS.md`.

   Ключевое отличие от п.2: там правило линтера служит спецификацией, здесь
   спецификацией служит **собственная декларация библиотеки**, а нарушение
   измеряется её же запуском.

2c. **Абстенция.** Если у выбранного файла нет улики, существовавшей до патча,
   прогон заканчивается отказом до первого обращения к модели. Патч, прошедший
   все гейты, но привязанный к тесту, который агент написал себе сам, тоже
   уходит в отказ. Это проверка в коде: просьба в промпте в этом проекте не
   работала трижды.

3. **Propose** — deep-read выбранного файла → LLM отвечает delimiter-форматом:
   `FILE` / `TEST_FILE` / `TEST_NAME` / `PROBLEM` / `RATIONALE`,
   `<<<OLD>>>`…`<<<NEW>>>` (замена) и `<<<TEST>>>`…`<<<END>>>` (pytest).
4. **Apply** — verbatim-замена; при промахе (LLM переотступил/сократил) —
   **AST-фолбэк**: символ находится по имени и подменяется целиком.
5. **До шести гейтов приёмки** (каждый включённый гейт обязан пройти):
   - **reproduce** — тест обязан **падать** на непропатченном коде (иначе патч ничего не доказывает);
   - `py_compile` + **targeted pytest**;
   - **regression** — не сломаны тесты пропатченного файла и его callers;
   - **CPU AutoML** — короткий `Fedot.fit` на пропатченном дереве (фреймворк реально работает);
   - **зонд рантайма** — набор случаев прогоняется до и после патча. Патч отвергается,
     если сломался хоть один **контрольный** случай (обычные данные перестали обучаться)
     или появился новый дефект. Если прежняя находка исчезла — это записывается в
     `probe_resolved` как доказательство настоящей пользы. Отсутствующий baseline
     считается отказом гейта; отключать проверку нужно явно.
     *Зачем отдельно от остальных:* тест агент пишет себе сам, а по литературе именно
     этот канал и эксплуатируют (Sakana AI CUDA Engineer нашёл дыру в коде проверки и
     обошёл контроль корректности; RL-дообучение поднимает долю жульничества с 0.6% до
     13.9%). Случаи зонда агент **не писал и не видит** — это наш аналог скрытых тестов.
     Самый дешёвый способ «починить» дефект — запретить все входы; контрольные случаи
     ровно это и запрещают. Отключается `FEDOTLLM_EVOLVE_PROBE_GATE=0`.
6. **Гейт настройки.** Если находка говорит «параметр нельзя использовать»,
   после патча операция обязана стать настраиваемой (`SimultaneousTuner`,
   6 итераций, `obtained_metric is not None`). Появился после патча, который
   прошёл все пять предыдущих гейтов и сделал хуже: агент убрал `iterations`
   из аргументов CatBoost — ошибка исчезла, объявленное пользователем значение
   стало молча выбрасываться. Инспекция параметров такое не видит
   (`implementation.params` показывает объявленное значение, перестал получать
   его только эстиматор); вопрос «а тюнится ли операция» видит.
   Отсутствующий результат считается отказом гейта. Отключается
   `FEDOTLLM_EVOLVE_TUNING_GATE=0`.

7. **Best-of-N** — до `FEDOTLLM_EVOLVE_CANDIDATES` независимых кандидатов,
   у каждого до `FEDOTLLM_EVOLVE_FIX_TRIES` self-fix попыток; побеждает первый прошедший все гейты.
8. **Audit** — `evolution_audit.md` + `proposal.json` в workspace.

LLM ходит только через `AIInference` (пресет `fedotllm:openrouter`).

## Запуск

```bash
export FEDOTLLM_LLM_API_KEY=sk-or-v1-...            # OpenRouter
export FEDOTLLM_REPO_PATH=../AutoDS-Tools/runs/fedot-evolve-demo/fedot
export FEDOTLLM_REPO_PYTHON=../AutoDS-Tools/runs/fedot-evolve-demo/.venv-fedot/bin/python

# один прогон
uv run python examples/run_fedot_evolve.py --override llm.model_name=openai/gpt-4o

# полный демо-путь (FedotAI → Supervisor → Evolve → pytest → CPU Fedot.fit → DEMO_QUALITY.md)
uv run python examples/demo_fedot_evolution.py

# честный success-rate по N прогонов → BENCH.md
uv run python examples/evolve_bench.py --runs 5
```

Supervisor route: `evolve` → один проход → `finish` (без зацикливания).

## Измеренные результаты

Модель `openrouter/openai/gpt-4o-mini`, локальный чекаут FEDOT, каждый прогон с чистого состояния.

**Главная метрика — «выход годного»: правки класса 1–2, а не success-rate.** Агент сам
ставит себе задачу, поэтому success-rate накручивается выбором задач полегче — ровно это
и произошло: конфигурация A дала 30/30 и **ноль** настоящих починок. За 150 прогонов
агент 26 раз «успешно» уточнил сообщение об ошибке и ни разу не тронул изменяемое
умолчание, `zip()` без `strict` или `print` в библиотечном коде.

Классы берутся **из кода правила линтера**, а не угадываются по тексту предложения:
угадывание завышало класс (прогон записался классом 1 лишь потому, что scout упомянул
аргумент по умолчанию, тогда как принятый патч правил формулировку ошибки).

Дополнительно меряем разнообразие целей: агент, который надёжно правит один и тот же
файл, репозиторий не эволюционирует.

| # | Конфигурация | Успешных | 95% CI | Уникальных целей | Топ-доля |
|---|---|---|---|---|---|
| A | базовая (свободный выбор) | 30/30 (100%) | [88.6%, 100%] | **1** — `api_data.py` | 100% |
| B | + заземление на `ruff` | 28/30 (93%) | [78.7%, 98.2%] | **1** — `data_definition.py` | 100% |
| C | + журнал памяти | 25/30 (83%) | [66.4%, 92.7%] | **6** | **43%** |
| D | + приоритет по серьёзности | **0/30 (0%)** | [0.0%, 11.4%] | 1 — `core/data/data.py` | 100% |

**Ключевые выводы:**
1. Заземление сменило цель, но **не сняло схлопывание** — при низкой температуре агент детерминированно берёт один и тот же аргмаксимум, сколько кандидатов ни покажи.
2. Схлопывание снимает **память между прогонами**: 6 целей вместо 1, различных найденных проблем 11 вместо 4–5.
3. За разнообразие платят надёжностью (100% → 83%): память выталкивает агента в незнакомые модули, где патчить труднее. Поэтому меряем **обе оси** — по одной success-rate «победила» бы вырожденная конфигурация A.
4. **Наведение на настоящие дефекты обрушивает агента в ноль (D: 0/30).** Цель он выбирает верно все 30 раз (`core/data/data.py`, где 6 дефектов `B008`) и тест пишет корректный — тот честно падает на исходном коде. Но починить не может: правка `B008` требует согласованного изменения в ДВУХ местах (умолчание в сигнатуре → `None` и конструирование объекта в теле), а формат нёс одну замену `OLD→NEW`. Модель склеивала обе правки в один хунк, и половина с телом попадала **внутрь докстринга** — синтаксис валиден, `py_compile` проходит, код мёртв. Гейты отработали верно: недоказанного не принято.
   **Вывод: 100% надёжности вариантов A–C — свойство одноточечных дефектов, а не починки вообще.**

Внедрено по итогам D (эффект ещё не измерен): **мульти-хунковые предложения** (несколько пар `OLD/NEW` на одно предложение, применение всё-или-ничего с проверкой AST) и **зондирование рантайма** (`probe.py`).

Затронутые модули в ветке C: `api_params_repository`, `api_data`, `assumptions_builder`, `data_definition`, `predefined_model`, `params`.

Побочный эффект заземления: промпт scout'а **сократился на 15%** (8.9k → 7.5k токенов), потому что точная локализация от линтера заменяет громоздкую секцию outlines.

Стоимость: ≈$0.0013 и ≈52–98 с на прогон, CPU-only.

## Принципы демо

- Только честные прогоны: ни в промптах, ни в retry не подсказываем конкретный файл/патч.
- Надёжность показываем числом (`evolve_bench.py`), а не одним удачным прогоном.

## Что измерено про потолок модели

Отдельный прогон на `openai/gpt-4o` (дороже `mini` примерно в 17 раз), всё остальное
без изменений: **0 из 5**, ценных правок 0. При этом сильная модель вела себя заметно
лучше — находила настоящий дефект класса 1 и проходила гейт воспроизведения, чего
`mini` не могла 138 раз. И всё равно ни одного завершённого прогона.

**Вывод: упирается не в мощность модели, а в конструкцию.** Покупкой модели задача не
решается — поэтому доказательство и вынесено из-под LLM в детерминированные шаблоны.

Попутно вскрылись две вещи, которые не работали молча:

- поле `FUNCTION` не заполняла **ни одна** модель, поэтому привязка к функции ни разу
  не сработала. Теперь символ вычисляется сам — по обратным кавычкам в описании
  проблемы, затем по имени и телу теста;
- хунк всегда был **один**, хотя `B008` требует правки в двух местах и это написано в
  промпте прямым текстом. Мульти-хунки заработали только когда тест стал приходить
  готовым: первый же прогон дал четыре хунка.

## Граница метода: что шаблоном не доказать

Шаблон строится **интроспекцией**, поэтому видит только объектную модель — сигнатуры
функций и атрибуты классов. Отсюда жёсткая граница покрытия:

| Класс дефекта | Находок | Шаблон |
|---|---|---|
| `B008`, `B006`, `RUF012` — умолчания и атрибуты класса | 46 | **да**, видно в `inspect.signature` / `vars(cls)` |
| `RUF013` — неявный `Optional` | 41 | да, но это класс 3 — на «выход годного» не влияет |
| `B905`, `S113`, `S608` — `zip()`, таймауты, SQL | 37 | **нет** |

Почему нет. `B905` выглядит так:

```python
for data_type, (name, _) in zip(self.data.data_type, self.data.items()):
```

Это вызов **внутри тела функции**, интроспекцией его не достать. Доказать дефект
поведением можно только вызвав функцию с последовательностями разной длины, а для этого
нужно построить `self.data` и весь контекст — в общем случае невозможно.

Соблазнительная замена — проверять исходник текстом («не осталось `zip(` без `strict`»)
— хуже, чем ничего: она подделывается добавлением `strict=False`, которое гасит линтер,
не меняя поведения.
